# 产品遗漏评审

日期：2026-09-13｜对应 [策划案](../PRODUCT_PLAN.md) v0.5｜状态：乙方评审建议，尚未执行运行实验。

## 1. 评审依据与判断

本次复核 v0.4 策划案和两份既有研究记录。兼容范围、来源失效、模型依赖、市场自身恢复、持续维护成本等已经记录，不能重复包装成新发现。当前主要空缺是资源发现、安装管理与用户完成任务之间，还有若干未定的产品和运行责任。

以下情形是用于暴露缺口的场景，不是声称故障已在本项目发生，也不是新增的甲方要求。

## 2. 需要补齐的八个问题

### B1：装完之后，用户在哪里完成任务

**场景：** 用户找到语音模型并下载完成，却仍不知道在哪里提交音频、如何开始转录、到哪里取得结果。我们现有的“使用入口”要求尚未细化到这些步骤。

**建议：** 每类拟交付流程明确入口、资源依赖、执行方、输出位置与故障入口。优先通过现有执行工具及 DSH 插件承接任务；确需新增执行功能时单独估算。完整市场管理与任务执行产品有不同职责，不能在开发中无声扩张，也不能用外部官网跳转替代已承诺的 DSH 内流程。

**验证：** E1/E6/E8 从一名用户的实际目标开始，到可检查的结果结束。

### B2：目录在哪里同步，平台服务承担什么

**场景：** 用户侧直接查询多个平台，与平台统一汇总后提供目录，会产生不同的联网条件、服务费用、缓存时效和故障依赖。现有“有缓存”尚未决定缓存由谁持有。

**建议：** 比较用户运行环境直接查询、平台集中同步、两者结合三种方案。初始候选为公共目录可缓存、账户专属内容和凭据保留在用户受控运行环境；是否需要平台服务由来源条件和实测决定。目录服务不可用时，已安装本地资源应按原有运行条件继续可用，外部服务依赖另外说明。

**验证：** E7/E9 记录每一步请求经过哪里；E4 验证目录服务失联时的实际使用与恢复边界。

### B3：连接多个来源，不等于拥有一个通用账户

**场景：** 目录访问、模型调用和 MCP 业务服务使用不同凭据。私有资源名称可能混入公共索引，自动从本地转向在线模型也可能改变内容接收方和费用。

**建议：** 分开来源连接、模型账户和 MCP 服务认证；记录凭据保存位置、接收方、作用范围与撤销方式。公共目录同步不上传用户工作内容或账户专属条目。自动切换遵循用户已经选定的数据去向与成本条件，缺少条件时停止该切换并解释原因；不把所有调用经我们服务器转发作为默认前提。

**验证：** E8/E9 检查凭据接收方、断开连接后的行为及路由约束。MCP 官方发布说明明确认证客户端凭据与签发方绑定；具体实现按目标协议版本核对。[官方说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

2026-09-13 另核查到 DSH 的[模型设置包](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/client/ui-settings-models/README.md)已有提供商管理、凭据引用和模型列表获取。我们需要明确市场如何接入既有能力，不能将问题描述为宿主完全没有账户与凭据机制。

### B4：目录变大后，用户是否更难找到东西

**场景：** 一个模型有多个量化版本和来源；用户用中文表达任务，返回列表却只有英文标签、重复卡片和来源热度。自动收录数量增加并不直接解决选型。

**建议：** 用真实任务设计用途搜索，补充中文与别名匹配、版本分组和来源关联。展示来源原始描述与平台整理说明的区别，解释推荐依据；缺少验证的资源保持可发现并明示状态。先做可解释的规则和小规模人工样例，不因这一问题先引入自动推荐系统。

**验证：** E7/E9 及用户研究比较找到目标资源的过程，包含重复来源、无结果、未知兼容和不同语言查询。样本量不用于宣称搜索全覆盖。

### B5：能返回一句话，不等于适合 Agent 工作

**场景：** 模型可以聊天，却无法正确调用任务所需工具；Skill 被加载，却依赖另一个客户端专有命令；MCP 服务同样标注 HTTP，双方支持的协议版本或扩展仍可能不同。

**建议：** 将支持声明关联到具体任务能力，例如工具调用、所需输入类型、结构化结果和流式行为，只测试实际流程需要的项目。模型、实际调用服务方、DSH 版本与必要适配配置共同构成验证对象。官方 MCP 已发布带协议与认证变化的版本，不能仅用“MCP”标签替代版本核对。[MCP 发布说明](https://blog.modelcontextprotocol.io/posts/2026-07-28/)

**验证：** 扩展 E6/E8/E9 的实际任务对照。OpenRouter 文档允许设置服务方回退与必需参数约束；因此模型名称本身不足以描述实际调用路径。其选项存在不代表 DSH 已经能传递或强制执行这些条件。[路由文档](https://openrouter.ai/docs/guides/routing/provider-selection)

### B6：部分成功之后，下一次操作从哪里继续

**场景：** 模型已下载，运行工具未装完，插件配置已写入，但启用失败；另一种情况是远端已接受任务，本地却因断网没有拿到结果。统一显示失败后重来，可能重复下载、配置或执行。

**建议：** 多阶段操作保留真实阶段结果，重启后识别已完成部分，允许继续或清理本次新增内容。不能保证一个按钮撤回所有外部行为；远端执行结果未知时先利用其任务状态或请求记录核查，缺乏证据时显示未知。只在有依据时重试，取消等待与取消远端任务分开。

**验证：** E4/E5/E6 在下载、写配置和激活边界设置中断对照；外部操作使用可控测试服务验证重复提交与取消行为。

### B7：环境保护对在线服务能承诺到哪里

**场景：** 本地配置和插件版本都没变，但远端模型别名、服务路由或服务供应发生变化。恢复本地配置并不能恢复已不存在的远端服务。

**建议：** 分别列出可按内容固定的本地资源、受来源可用性约束的重新下载，以及无法由我们冻结的在线依赖。保留可用内容、版本和路由条件；云端服务停止时提供明确状态与替代选项，不能把替代服务称为原环境恢复。

**依据与验证：** Hugging Face 下载支持指定提交，而默认下载会跟随最新修订；这说明记录名称或链接不等于固定内容。固定提交也不能保证来源永不删除内容。[下载文档](https://huggingface.co/docs/huggingface_hub/guides/download)。E4/E9 分开验证本地恢复、来源文件失效和在线服务变化。

### B8：第一条值得迁移的流程和排障责任仍未确定

**场景：** 用户通过原工具本来就能调用模型或添加 Skill；多一个市场若仍要求用户自己查配置和追问各方，就没有证明迁移价值。出错时，用户也不应先自行判断是市场、DSH、资源作者还是服务方的问题。

**建议：** 这是第 3、8、9 节已经记录但尚未解决的问题。首轮用少量完整任务与现有方式对比，记录首次安装门槛、必要账户、实际完成结果及恢复过程。市场提供统一的问题入口，再按证据说明责任和下一步，不对第三方作我们无法兑现的修复时限承诺。

**验证：** E1、首次用户观察和故障复现记录。真实迁移理由、分发入口与维护资源仍属待验证，不以资源数量或界面完成度代替。

## 3. 决策顺序

先解决 B1—B3：乙方提交代表性用户流程、目录同步位置与服务依赖比较、账户和数据流向；甲方判断体验、投入及可接受条件。B4—B8 跟随对应实验细化，不要求甲方在会议中设计内部技术方案。

可用于首轮验证的场景候选如下，具体首发范围尚未由本记录决定：

| 场景 | 完成标准 | 能暴露的问题 |
|---|---|---|
| 为现有 DSH 添加一个有明确外部工具依赖的 Skill | 找到来源，完成 MCP 配置与 Skill 添加，在 DSH 中完成指定任务并取得结果 | 来源、依赖、认证、作用域、调用与失败责任 |
| 为现有 DSH 选择并接入一个能完成工具任务的模型 | 发现候选、理解运行或账户条件、连接后完成同一工具任务 | 搜索质量、模型能力、服务路由、调用成本 |
| 为一个语音任务准备所需模型与执行工具 | 从资源发现走到可检查的转录或语音结果，并展示一次中断恢复 | 多模态使用入口、运行职责、结果位置与部分成功 |

评分社区、自动推荐算法、通用工作流编辑器与大规模托管服务可以后置；解决这些问题不要求先把它们全部建出来。先用现有 E1—E9 验证可交付流程，再决定是否需要额外模块。

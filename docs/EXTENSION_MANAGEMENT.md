# 扩展安装与管理

当前开发版本在“我的资源 → 已安装扩展”统一管理原生 DSH bundle 与 dsh-std 组件。适用环境：Windows、Node.js 24、DSH `0.1.5-rc.2`，标准适配器固定为 `@dsh-std/adapter-dsh@0.1.1-rc.3`。商城自身已有经官方 CLI 安装与卸载验证的独立开发包，见 [商城安装](PACKAGE_INSTALLATION.md)；尚未公开发布。

## 使用流程

1. 输入完整 npm 包名与固定版本，例如 `@dsh-std/adapter-dsh@0.1.1-rc.3`，点击“检查安装”。资源详情中的 npm 包也可以带入此页面。普通模块没有 bundle 或标准入口时不会安装。
2. 核对目标 profile、版本、运行方式、许可证、声明权限与兼容结果。预览只读取元数据和发布包，检查 SRI、根声明及入口文件，不加载插件代码。
3. 确认后调用官方 `dsh plugin --profile <profile> add <name>@<version> --ignore-scripts --save-exact --registry=https://registry.npmjs.org`。安装前保存配置备份，执行后核对直接依赖版本、已安装包与 bundle 记录。
4. 成功显示“需要重启”。重启 DSH 后刷新状态；入口已加载不保证每项功能可用。标准组件要求先加载适配器，缺少时可先检查并安装上述固定版本。
5. 更新时输入新的固定版本，重新检查与确认；卸载使用官方 `remove`，保留插件数据及共享依赖。适配器、DSH 基础包和市场自身受保护；存在直接反向依赖时拒绝卸载。

下载文件与安装是两个独立动作。Prompt 使用、Skill 文件、MCP 连接配置和纯主题文件沿用各自流程，不自动包装为可执行插件。

## 兼容检查与边界

- 检查 `engines.dsh`、`engines.node` 及可解析的 DSH peer 版本；未声明宿主范围时明确显示待验证。
- 标准组件使用官方清单解析、声明定义验证和实际适配器协议协商。未知定义或缺失协议阻止安装。该检查不能代替运行、权限执行或第三方代码安全审计。
- 同时声明原生与标准入口的包暂时拒绝安装。两套运行时均会自动发现入口，仅记录用户选择不能防止重复加载。
- 源码、host facets、bundle 必须有受支持的清单与包内入口。仅支持 npm 官方固定版本、4 MiB 压缩包和 32 MiB 解压上限；不支持任意 URL、版本范围或本地路径安装。
- 预览校验的 SRI 被记入操作记录；官方 CLI 按名称和版本再次获取包，尚未把预览的字节直接交给 pnpm。传递依赖由 profile 锁文件记录，尚无完整供应链审计。
- 预览有效期 10 分钟；当前市场实例最多保留 64 个预览、128 个请求。页面重复点击或丢失响应重试复用同一操作；该结果缓存不跨宿主重启。独占文件锁跨进程生效，但不能阻止外部编辑器或另行运行的 CLI。

## 中断与恢复

记录位于 `DSH_HOME/community/operations/<操作编号>/`：`journal.jsonl`、`cli.log`、`backup.json` 与 `backup/`。备份包含 `package.json`、`pnpm-lock.yaml`、`cordis.patch.yml`，不包含 node_modules、包缓存、会话或插件数据。这些文件可能含本机配置，不要提交到 GitHub。

执行失败、超时、进程中断或校验不一致时，保留 profile 下的 `.dsh-market-installer.lock`，阻止后续写入。操作前和真正调用 CLI 前均检查配置指纹，外部变更会使预览失效。

恢复目前需要人工核查：先停止对应宿主，确认本次 CLI 及其 pnpm 子进程已结束；按操作编号检查日志、当前依赖和备份，保留中断后的外部修改；修复并验证依赖、bundle 与实际加载后，才移除该 profile 的操作锁。不能只覆盖锁文件就宣称回滚成功。尚未提供自动回滚、图形化恢复、单组件热启停或第二宿主版本的保证。

## 验证

运行 `npm run verify`。其中 `node integration/verify-compatibility.mjs` 在新建的隔离 profile 中通过市场执行器安装真实公开适配器，再通过官方 CLI 安装明确标注的原生/标准测试包，验证两者实际运行、卸载原生包及重启后标准组件保留。测试包不是社区收录资源，也不代表所有第三方包已通过验收。

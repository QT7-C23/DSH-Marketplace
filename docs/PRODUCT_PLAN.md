## 1. 项目主张与当前判断

建设一个由我们主导、在 DSH 内使用的社区资源市场与管理平台，首发聚焦插件、Skill、MCP、Slash、Prompt、主题六类资源。市场连接受支持的发布源和目录，自动发现和更新资源信息；乙方主动寻找和评估这些资源的来源。用户能在同一入口发现资源、选择合适版本、完成对应的安装或接入流程并实际使用，在环境变化前了解影响、在受支持的失败场景下恢复。配套研究和建设兼容层，把可以集中处理的上游变化从插件作者手中接过来。

甲方已按 R35 确认：原生 DSH 资源与符合 dsh-std 的组件同时纳入我们维护的统一兼容层，共用市场和管理流程，各自保留接入机制、能力边界及验证结果。双路径是建设范围，具体支持版本和兼容承诺由实测确定。

本文用“资源”统称这些内容，“插件”专指需要加载执行的扩展。Prompt 现为甲方提出的首发类别，按可预览、填参、放入当前任务的提示词模板设计；GitHub 投稿文件、无账号本机收藏、从市场返回当前会话并追加草稿，已在 DSH 0.1.5-rc.2 验证。六类资源共享发现与管理体验，各自的生效条件和兼容判定分别设计。

甲方进一步明确：六类资源均支持用户向社区上传和分享，帮助社区积累可复用内容。市场同时承接社区投稿与外部来源自动发现，支持作者发布、维护和接收反馈；不能只做由平台填充内容的目录。

**当前范围调整：** 暂缓 Hugging Face、Civitai、OpenRouter、Ollama 等模型目录接入，以及本地模型下载、运行环境配套与 Cookbook；主题按 R33 恢复为第六类，先接通分类与投稿，再验证真实来源、应用和恢复。保留此前研究，不安排自动进入下一版的承诺。用户继续使用 DSH 已配置的模型；商城不接管模型供应与推理设置。OpenRouter 提供在线模型 API，其性质与下载本地权重不同，此处同样暂缓的是商城模型目录功能。[OpenRouter 官方说明](https://openrouter.ai/docs/quickstart)

乙方赞成这一收敛：它减少大文件分发、模型格式、执行工具与硬件适配工作，让首发围绕 DSH 内的任务能力展开。“大部分用户用不上本地模型”目前是甲方的使用判断，尚无用户比例证据；本次取舍不依赖把它当作统计结论。

甲方所说的 Minecraft 体验，在本项目中拆成三个成果：

1. **好找、好装、好管理**：市场与资源管理器提供连续的用户流程，安装后能找到使用入口。
2. **已有环境可持续使用**：明确环境版本，控制更新，提供经过验证的恢复流程。
3. **迁移新版少改插件**：通过共享接口和适配器吸收一部分上游变化，并明确支持范围。

乙方判断：值得进入调研与技术验证阶段。完整市场有清楚的用户形态；兼容层有需要验证的工程路线。当前不能承诺市场占有率、跨全部版本兼容或确定工期。

**产品目标保持完整，实施范围按证据收敛。** 市场不因兼容实验困难被擅自改成只读报告；兼容层也不因市场能够开发就被视为已经解决。

## 3. 第一批用户与价值假设

以下为乙方建议，需用户研究确认，不能当作已经存在的市场需求规模。

| 人群 | 要完成的事情 | 我们希望提供的价值 | 如何验证 |
|---|---|---|---|
| 已使用 DSH、会安装插件或其他资源的个人用户 | 找到可用资源，管理已有环境 | 减少查资料、手改配置和失败后的恢复工作 | 观察真实安装、接入、升级与恢复过程 |
| DSH 新用户 | 不理解包名和配置，也能加上想要的功能 | 有引导的发现、安装和配置流程 | 观察首次使用的卡点与求助次数 |
| 插件和资源作者 | 发布资源并明确支持范围 | 少重复填写资料、获得可复现的问题报告；在适配范围内减少改动 | 用实际插件、Skill、MCP 配置或 Prompt 验证发布和接入流程 |
| 整合包或界面维护者 | 管理一套可重复安装的插件组合 | 有版本记录、来源信息和恢复依据 | 后续通过真实组合验证，暂不设为首发唯一客户 |

建议优先研究第一类用户，并保留新用户体验。原因是他们更容易提供真实问题和复测机会；这一选择不意味着产品长期只服务技术用户。

差异化假设：用户可能愿意为“少出错、出了问题能恢复、迁移新版更省事”的完整体验增加一个市场入口。即使某个功能已有竞品实现，流程质量仍可比较；目前没有证据证明我们的组合一定更好。

| 市场与内容目录 | 连接资源来源，自动发现，按用途和类型搜索、浏览详情、选择版本 | 来源连接、字段归类、身份关联、内容同步、状态说明 | 来源接口、覆盖范围、访问条件和更新可靠性 |
| 资源与环境管理 | 按类型完成安装、配置、接入、启停、更新、卸载、恢复 | 操作编排、实际状态同步、失败处理 | 外部修改、共享资源、数据迁移、重启和执行依赖 |
| 兼容检测 | 看懂资源在目标环境下测过什么 | 按类型建立可重复测试、结果记录、失败分类 | 插件加载、Skill/命令执行、MCP 调用和 Prompt 填参与使用分别验证 |
| 兼容运行层 | 在承诺范围内减少插件随上游变化的改动 | 稳定接口、针对宿主版本的适配、契约测试 | 无法通用代理所有内部调用，作者采纳也有成本 |

面向用户的主流程：

```mermaid

    A[打开 DSH 内市场] --> B[确认当前环境]
    B --> C[查找资源并选择版本]
    C --> D[查看安装影响]
    D --> E[按类型安装或接入]

    F --> G[管理与升级检查]
```

### 4.1 市场与管理界面

建议保留五个清楚的入口：发现资源、资源详情、我的资源、更新与兼容、环境与恢复。发现页支持按用途浏览和按资源类型筛选；“我的资源”区分已获取、已启用和待配置等实际状态。首装引导和故障提示贯穿这些流程。

- 资源详情应说明用途、作者与来源、资源类型、适用条件、可选版本、必要配置、依赖和已知问题，并展示实际使用入口。
- 已安装页展示真实安装与运行状态，区分已安装、待配置、已停用、待重启、加载失败。
- 不把“有更新”写成“应该立即更新”，不把“没有测试记录”写成“不兼容”。
- 进度必须来自真实操作；没有下载量、评分或截图时，不用样例数据填充成产品事实。
- 普通用户看到问题影响与可选动作；日志、协议名和测试细节放在可展开的说明中。

Codex 是甲方明确偏好的体验参考，Pivot 是多类资源组织和交互的主要参考。本稿先规定学习方向，详细布局、视觉风格和框架仍待后续设计；不把参考产品的外观或技术实现直接复制为要求。

### 4.2 安装市场本身

在 DSH 内使用市场，需要先解决市场的安装入口。乙方建议评估简短的首次安装流程、现有发行版集成和可选辅助安装器；不默认已经获得官方内置位置。

建议优先验证 DSH Web 中的集成，因为本轮已有文档先例；Web、TUI、桌面壳的首发优先级仍待讨论。操作系统也未确定，不能用开发机是 Windows 推导全部目标用户都在 Windows。

### 4.3 多类资源的发现、使用与管理

| 类型 | 用户理解 | 从发现到可用的最小流程 | 关键兼容与管理条件 |
|---|---|---|---|
| 插件 | 为 DSH 增加功能 | 选择版本 → 安装 → 必要配置 → 加载 → 使用 | 宿主与接口版本、依赖、权限、生命周期和恢复 |
| Skill | 让 Agent 按一套方法完成任务 | 查看用途和示例 → 添加 → 选择生效范围 → 调用 | 格式、所需工具或脚本、范围、冲突及实际调用能力；已添加不等于每次自动执行 |
| MCP 服务 | 让 Agent 连接外部工具或服务 | 发现服务 → 选择本地启动或远端连接 → 配置 → 连接并读取工具列表 → 验证调用 | 传输、运行依赖、认证、作用域、工具能力与断连；目录条目不等于已运行的服务 |
| Slash 命令 | 输入 `/命令` 快速发起操作 | 查看用途 → 获取所属插件或相应能力 → 检查重名 → 注册 → 调用 | DSH 已有原生命令接口；参数、作用域和依赖分别验证，其他产品的命令文件不能直接视为通用安装包 |
| Prompt | 复用一段任务输入 | 查看示例 → 收藏或添加 → 填入变量 → 预览内容 → 放入当前任务后由用户发送 | 缺少变量须提示；不覆盖已有草稿，不因收藏而执行；与 Skill、MCP Prompts 分别定义 |
| 主题 | 调整 DSH 界面外观 | 查看效果和版本 → 安装主题插件或通过父插件导入配色 → 应用 → 检查 → 恢复 | 区分插件与数据文件；验证深浅色、界面版本、依赖、共存及卸载恢复 |

统一列表共用名称、用途、作者、来源、版本、类型和状态。详情展示各类型专属信息，主操作使用“安装”“添加”“下载”“连接”“预览”等准确文案。技术差异由产品解释，用户不用先理解包结构才能选择。

六类资源不等于六套独立安装系统。Skill 表达任务方法与所需资源，Prompt 表达可复用输入，Slash 提供调用入口；一项能力可以同时具备三者，应展示关联而非重复制造安装。插件包和 MCP 本地服务仍可能需要下载程序、Node.js 或 Python 等执行依赖；暂缓模型下载不等于取消这些必要处理。远端 DSH 的安装、配置和执行位置必须指向运行主机。

一个能力包可以包含插件、Skill、MCP 连接定义、命令、Prompt 或主题。建议允许资源单独发现，并在详情显示“包含哪些资源、来自哪个包、哪些已存在”。共享资源记录归属和被依赖情况，卸载一个包时不得误删其他包仍需使用的内容。依赖额外模型权重的条目可说明条件，但首发不承诺代装或验证这些模型，也不将其作为无额外条件即可使用的样本。

这要求“目录条目、实际分发包、安装后的资源”能相互关联；不必强行做成一物一包，也不能把不同资源在内部全部伪装成可执行插件。具体数据合同在实现设计中确定。

### 4.5 六类资源的外部自动发现

甲方希望商店能够持续连接外部服务、自动找到可能有用的资源。当前按 R17 与 R33 将这项能力用于六类首发资源；每个来源都需要实际接入，不能承诺输入任意服务器地址即可识别所有资源。插件发布资料可暴露其 Skill、Slash、Prompt 和主题；缺乏结构化资料的内容保持待适配，不能把普通网页中的指令当作可直接安装资源。

用户流程为：**选择或启用来源 → 自动获取资源列表 → 按任务搜索筛选 → 查看版本与使用条件 → 安装、添加或连接 → 验证实际使用**。自动发现不自动安装、授权、启用或执行资源。

| 能力 | 产品应做到什么 | 验收边界 |
|---|---|---|
| 来源连接 | 展示已接入来源、连接状态、必要账户配置及最近成功更新时间 | 能区分未连接、无权限、请求失败与确实没有结果 |
| 自动发现与更新 | 按来源能力分页查询、搜索和定期更新，支持手动刷新 | 使用真实条目与版本；说明当前查询范围，不把一页结果称为完整收录 |
| 统一整理 | 保留原始来源、资源 ID、版本与文件关系，映射到统一筛选字段 | 同名不自动合并；身份或内容依据不足时保留为不同条目 |
| 使用条件说明 | 展示获取条件、格式、宿主与工具依赖、必要账户及已验证情况 | 缺失字段显示未知；来源标签不能自动变成“在此 DSH 可用” |
| 持续可用 | 缓存已有目录，处理限流、中断、凭据失效和来源内容变动 | 一个来源故障不阻塞其他来源；显示缓存时间，不把请求失败当作资源下架 |

来源连接负责发现与更新；资源管理负责获取、配置及生命周期；DSH 与选定执行工具负责实际任务。精选推荐可以与自动汇总并存，但不得以人工审核或我们的签名目录作为所有外部条目被发现的前提。来源提供的信息、平台核查结果和本机验证结果分别展示。

#### 暂缓的 Model Hub 设计参考

下列内容保留历史设计，不参与当前首发排期、费用和验收。重新纳入模型资源时再核查。

模型筛选采用几个独立维度，避免将用途、文件类型和来源混成一个分类：

| 维度 | 示例 | 作用 |
|---|---|---|
| 任务 | 文本生成、视频生成、语音识别、语音合成 | 回答用户要完成什么 |
| 资源角色 | 完整模型、LoRA/适配器、其他配套组件 | 说明是否需要基础模型和配套资源 |
| 格式与运行方式 | 文件格式、量化规格、支持的执行工具、目标主机 | 判断如何运行，硬件要求需区分估算与实测 |
| 来源与获取条件 | Hugging Face、Civitai；公开、需登录或需申请访问 | 说明从哪里获取、当前是否有获取条件 |

例如，找到用于视频生成的 LoRA 后，详情需要指出匹配的基础模型与运行方式；它可以同时属于“视频任务”和“LoRA 组件”。基础模型字段缺失时说明待确认，不凭名称猜测兼容性。[元数据参考](https://huggingface.co/docs/hub/model-cards)

模型来源发现、权重下载、模型运行与 DSH 接入原本是分别验证的职责；暂缓时一并从首发移出，后续不因保留研究就自动进入开发。

### 4.6 来源范围与主动发现机制

以下为此前研究形成的候选，按 R17 更新优先级，不代表已实现。首发调查插件发布源、Skill 来源、MCP 注册表，以及作者提供的 Slash/Prompt 内容；具体能力与限制见 [资源来源与 DSH 扩展核查](research/2026-09-11-resource-sources-and-dsh-extensions.md)。

| 来源类别 | 已知候选 | 市场应提供的流程 | 需避免的误判 |
|---|---|---|---|
| 插件发布源 | 作者发布仓库、npm 包与受支持的目录清单 | 自动获取发布资料、版本和依赖，追溯并安装实际包 | 普通 npm 包不等于 DSH 插件；目录条目与安装包需关联 |
| Slash / Prompt 来源 | 所属插件清单、作者仓库及可解析的资源目录 | 提取有明确归属的命令和模板，保留变量、版本与使用条件 | 尚无通用跨客户端格式结论；来源覆盖与转换规则仍需实测 |
| Skill 来源 | 作者官方仓库、Anthropic Skills、skills.sh 等目录 | 自动发现条目并追溯原始资源，获取完整 Skill 目录，验证格式、依赖和调用条件 | 不能只复制 `SKILL.md` 而丢失脚本和素材；公开可见不等于许可相同或适配 DSH |
| MCP 来源 | 官方 MCP Registry、兼容注册表、服务商官方发布 | 同步服务元数据，按包或远端地址配置，连接后验证所需工具 | 注册表提供发现资料；服务的运行、认证和功能支持仍需验证 |

乙方负责补充来源调查表，按实际新增内容、官方接口或发布格式、访问稳定性、更新条件和接入成本排序。新增来源优先复用已有注册表或 Git 仓库接入方式；特殊服务单独适配。有公开网页但未找到稳定接口的，保留来源候选和问题记录，不用抓取成功一次证明长期自动同步可用。模型权重目录、Ollama 生态、OpenRouter 与厂商模型目录均保留在历史研究中，本轮不继续接入。

产品建议提供来源管理：内置来源、已支持格式的自定义来源、来源状态和刷新入口。发现新站点、接入新来源、同步该来源内的新资源是三个不同工作；未来新增适配器不能要求用户重新设计市场。外部目录里的全部 Skill 和 MCP 条目也不应直接进入 Agent 的工作上下文，只激活用户选定且满足条件的资源。

### 4.7 Slash、Skill 与 MCP 的 DSH 接入边界

2026-09-11 读取 DSH 官方 `master` 对应提交 `c291e7961a515f6d7af9304e7fd1d257929aef26` 的资料及部分命令实现，确认如下：

- **Slash 有原生扩展接口。** 官方 `dsh-commands` 允许插件通过 `ctx.commands.register()` 注册命令，交互式 CLI/Web 消费命令目录。优先沿该接口实现；无需先把修改上游源码作为前提。同一作用域重名、参数处理、卸载和界面刷新需要实测。无界面运行及 ACP 自动化没有该交互命令入口。[官方包说明](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/interaction/commands/README.md)
- **Skill 有发现与加载机制。** 官方注册表可接入不同来源提供者，本地提供者读取指定目录。采用通用 Skill 格式仍需检查 DSH 的目录规则、依赖、作用域以及用户/模型调用策略；本轮不承诺其他客户端的命令或专属工具语法直接通用。[官方 Skill 说明](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/docs/subsystems/skills.md)
- **MCP 有现成客户端，但能力有边界。** 官方 `dsh-mcp-client` 支持 stdio 和 Streamable HTTP，当前桥接工具调用；Resources 和 Prompts 尚未支持。市场应展示所需能力是否匹配，再验证连接与调用。[官方 MCP 说明](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/mcp/mcp-client/README.md)

“协议”分别核查技术接口、社区互操作约定和开源许可证。DSH 官方仓库采用 MIT 许可证；这不能代替技术兼容性判断。R35 确认纳入的 dsh-std 路径，其适配器文档已有 `CommandRuntime` 映射，但发布到具体界面仍需相应位置提供者，必须与目标 DSH 版本配套验证。[DSH 许可证](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/LICENSE)、[标准适配器说明](https://github.com/Yan-Zero/dsh-std/blob/main/packages/adapter-dsh/README.md)

乙方建议：保留 Slash 的发现和管理目标，首选由插件或相应能力提供命令，逐项验证注册、可见、执行与移除。跨产品命令导入单独评估转换条件；不需要为维持统一商店外观而假定存在统一 Slash 文件协议。

**Prompt 的首发定义另行落实。** 本市场的 Prompt 指提示词模板，不依赖 MCP 的 Prompts 能力。2026-09-13 复读上述固定提交的 MCP 说明，其桥接仍仅覆盖 Tools。市场需验证模板预览、变量替换和当前任务输入的宿主接口；该能力属于拟建设功能，不能称为已存在的原生 Prompt 商店。

## 5. 必须走通的使用场景

| 场景 | 用户动作与预期结果 | 不满足时应如何处理 |
|---|---|---|
| 第一次使用 | 识别 DSH、环境位置和已有插件，说明哪些可管理 | 找不到或不支持时解释原因；不写入猜测的配置 |
| 安装插件 | 选用途和版本，看到依赖及配置需求，完成后能使用 | 保留失败原因和已有环境；不能只弹“安装成功” |
| 管理已有插件 | 识别外部装入的插件，显示来源，选择是否纳入管理 | 未取得管理条件时只展示；不覆盖手工配置 |
| 修改配置或停用 | 说明影响哪些功能，保存后核对实际状态 | 需要重启就明确提示，失败则恢复本次可恢复变更 |
| 更新单个插件 | 预览版本、依赖和配置变化，完成验证后生效 | 更新失败不会把旧的可用安装直接丢弃 |
| 升级 DSH 环境 | 保留旧环境，验证新版及关键插件，再切换 | 未验证项明示；不默认为用户升级全部组件 |
| 故障恢复 | 能找到上一个可用状态和本次变更记录 | 说明恢复覆盖范围；无法恢复的数据不可宣称已恢复 |
| 作者发布新版本 | 提交来源、支持条件和验证资料，修正反馈 | 身份未确认、材料不足、测试失败各有独立状态 |
| 用户向社区分享资源 | 选择类别，上传内容或提交发布源，填写用途与示例，查看发布状态并维护后续版本 | 缺少资料、内容重复或检查未通过时给出可修改原因；保存草稿不等于已经公开 |
| 使用 Skill 或命令 | 添加后在指定范围实际可发现并调用，能看清依赖 | 格式不支持、缺少工具或命令重名时解释处理方式 |
| 使用 MCP 服务 | 从来源发现服务，完成本地启动或远端连接配置，读取工具列表并验证所需操作 | 区分包已获取、连接失败、认证缺失和工具能力不支持；移除本地连接不宣称删除远端服务 |
| 使用 Prompt | 预览用途与示例，填写变量，将完整输入放入当前任务并由用户发送 | 缺少变量或目标会话不明确时提示；保留已有草稿，不静默执行 |
| 自动发现资源 | 启用受支持来源，自动获得真实列表，搜索、筛选并查看更新 | 单个来源失败单独显示；保留可用缓存，不以空列表掩盖连接故障 |

所有修改遵循“检查现状 → 展示影响 → 执行 → 核对结果 → 记录恢复依据”。市场可以调用宿主 CLI 实现操作，但应在产品内完成编排与结果反馈。外部工具依然可能改动环境，我们需要检测冲突，不能假定独占所有写入。

### 5.1 环境保护的具体含义

“环境”至少要能识别 DSH 运行时、必要的执行环境和依赖、适配层、插件版本、配置及数据归属。独立配置目录或 profile 不能直接证明运行时已经独立；必须实测全局升级是否会影响被保留的环境。

恢复要分开描述：包文件恢复、配置恢复、插件数据恢复、外部行为恢复。插件修改工作区、调用远端服务或执行不可逆数据迁移时，降级一个安装包不等于撤销这些行为。

**市场本身失效时也要能恢复。** 首发需有不依赖市场页面加载成功的恢复入口，并实测市场插件更新失败、DSH 无法正常启动时的处理。它可由轻量辅助工具承担，不因此扩展为一套完整桌面客户端。

### 5.2 兼容状态的表达

来源声明、测试结果和测试新鲜度分别记录。示例用语为：作者声明支持、在此环境完成加载测试、在此环境完成指定功能测试、已知不兼容、尚未验证。超时、缺少凭据、网络失败标为测试未完成，不能直接统计为插件不兼容。

每份测试结果关联具体插件内容、DSH 版本、适配层、相关依赖、操作系统、测试条件、步骤与时间。用户只看摘要，技术人员可展开证据。已签名只说明来源和完整性；旧测试可以触发复测，不因时间经过就被改写为历史失败。

上述运行测试主要描述可执行插件。Skill 和命令需要验证发现、参数、依赖与调用；MCP 需要验证传输、认证、工具发现及目标操作；Prompt 需要验证变量、预览、当前任务输入和发送前控制。所用模型及其任务能力作为测试条件记录，由 DSH 已有配置提供。这些状态分别记录，不能因为插件已加载就给整个能力包的全部资源标为可用。

多个插件各自通过，不能证明一起使用没有冲突。首发除单插件测试外，需要覆盖典型组合以及配置、依赖与生命周期冲突。

### 5.3 从资源可用到用户任务完成

乙方需要为每条拟交付流程补齐五个答案：用户从哪里开始、需要哪些资源、谁执行任务、结果在哪里取得、失败后从哪里继续。例如一项资料整理能力，应从选择 Prompt、添加所需 Skill、连接检索 MCP，走到 DSH 内取得带来源的结果；具体场景为验证候选，尚非确定的首发内容。

建议以 DSH 与现有工具承接任务，市场负责资源准备、接入和清晰的使用入口。需要新执行插件时单独列出范围与成本；不以跳转外部官网代替承诺在 DSH 中完成的流程。六类资源可共同完成一项任务，也应各自有可独立验收的使用路径。

跨资源操作需记录每个阶段的实际结果。下载完成、配置写入和启用失败可以同时存在；重新打开页面应能识别已完成部分并选择继续或清理。远端操作结果未知时先核查状态，不能直接按失败重发；取消本地等待也不等于远端任务被取消。

### 5.4 下一步策划交付的具体含义

乙方为六类各找一个有代表性的实际资源，分别写清两个人的经历：作者如何上传、发布与更新，使用者如何发现、理解、获取并真正用起来。样本用于检查流程，不限制商城每类的收录数量，也不要求甲方自己找样本或决定技术实现。

例如作者填写周报模板并发布，使用者搜索后填写工作记录、预览并放入当前任务；使用反馈帮助作者更新内容。[自编 Prompt 样本](examples/weekly-report-prompt.md)及社区 Prompt 已完成本机 DSH 使用验收。官方规划插件及其 Slash、内部沟通 Skill、文件系统 MCP 仍为待实际安装或调用的参考样本；各类证据不能互相替代。

这份材料让甲方评审“这样分享和使用是否方便”；乙方据此形成页面清单与实现顺序。[首版流程](FIRST_RELEASE_FLOWS.md)已对应可点击原型、宿主市场、本机社区及指定来源更新验收。后续仍需扩大来源覆盖、其他四类实际使用、用户验证和有依据的投入估算。

### 6.1 已确认的统一兼容层与实现选择

原生 DSH 与 dsh-std 是同一兼容层内并存的接入路径，不作为互相替代的产品方向。统一层负责身份、环境、依赖、操作状态与恢复依据；底层分别调用原生机制或标准适配器。六类资源按实际形态接入，标准标签不成为第七类资源。完整边界与验收以 [资源兼容与主题支持](COMPATIBILITY_AND_THEMES.md) 为准。

下表比较实现方式，不再用于决定是否纳入标准组件：

| 路线 | 预期收益 | 代价与适用边界 |
|---|---|---|
| 复用现有标准和适配器，补足缺口 | 作者可复用已有接口，减少重复建设 | 受其覆盖、版本演进和维护质量影响，需测试验证 |
| 在现有协议上实现我们维护的适配器 | 保留互操作性，同时掌握宿主适配和发布节奏 | 需要自己承担实现和回归测试，不能只改名复用 |
| 自定义一套插件接口与兼容运行层 | 对接口和产品行为有更多控制 | 作者迁移、文档、工具链和长期维护成本更高 |

实施先比较前两种方式；自定义接口仅在真实缺口需要时另作论证，不能据此取消已确认的原生与标准接入范围。评价依据为可吸收的变化、所需插件改动、覆盖缺口和维护成本，不根据 star 数预判。

存量插件需要分情况：遵循选定接口的插件可获得承诺范围内的适配；直接调用 DSH 内部实现的插件以原生兼容测试为基础，必要时做针对性迁移。不能承诺用一个通用代理让所有存量插件零改动受益。

兼容检测和两条路径的适配验证从早期开展。先在当前固定宿主验证原生与标准组件独立运行、混合共存、失败恢复及共享依赖，再固定第二个宿主版本验证适配收益。发布时按实测公开支持范围；未完成标准路径前不宣称双路径已经交付。

## 7. 完整范围与分阶段交付

资源类别按 R17 收敛模型部分，并按 R33 恢复主题；具体支持的环境、格式和来源仍待实验确定。这里的阶段划分不是已经承诺的日期。

首发目标为插件、Skill、MCP、Slash、Prompt、主题六类，每类以一条真实可用流程定义交付。实现可分步，但未完成某类流程时明确标记，不能把空入口或样例卡片称为六类支持。模型目录、下载与运行配套、Cookbook 不纳入首发；以后是否恢复投入另行评估。兼容运行层主要服务可执行扩展，其余资源使用各自的生效与兼容规则。

| 共享兼容层 | R35 确认原生与 dsh-std 双路径；早期完成独立运行及共存实验，发布能力以实测为准 | 扩大稳定接口和支持版本 |
| 社区上传与作者维护 | 六类均有用户可操作的投稿入口、内容或发布源提交、状态反馈、版本更新与问题反馈；后台必要处理可人工执行 | 批量发布、协作维护、更完整的作者后台 |

| 付费插件、企业目录、云同步 | 未确定，不构成当前交付条件 | 需要单独产品与资源论证 |

配置编辑、依赖处理和诊断提示属于支持插件正常使用所必需的部分，不能为了缩小范围被一概删除。首发也不需要实现每一种配置编辑器或复制竞品全部功能。

### 阶段与验收出口

| 阶段 | 我们交付什么 | 通过标准 |
|---|---|---|
| A：需求与可行性收敛 | 竞品实测、用户问题记录、关键技术实验、范围建议 | 能解释用户为何需要、首发支持什么、承诺有哪些证据；缺口有处理方案 |
| B：内部完整流程 | DSH 内六类资源市场、社区投稿、外部来源自动发现、分类管理、更新恢复、兼容摘要 | 六类各有作者发布和用户使用样本；来源真实可追溯，失败和外部修改不会被伪装为成功 |
| C：受控试用 | 可安装发行物、引导、帮助和恢复工具、支持矩阵 | 非开发者按引导完成主要任务；关键问题有复现和修复记录 |
| D：公开测试与维护 | 发布流程、变更记录、上架下架流程、支持政策 | 有可持续的版本验证和故障处理能力；宣传与实际能力一致 |

A 阶段内，市场原型与兼容层实验可并行；不要让一个无限扩大的底层体系阻塞全部产品验证。任何未通过的实验只影响其对应承诺，不能随意推翻全部产品方向。

首发支持矩阵至少要明确操作系统、DSH 版本、界面入口、插件形态、适配层版本、六类资源的来源与格式、作用域、依赖和已验证组合。来源可查询、内容可获取、功能可使用分别列明。所用模型作为任务测试条件记录，不转化为模型供应能力承诺。暂不填写猜测的版本号；后续依据实际安装和测试结果固定到具体版本或提交。

## 8. 关键不足、风险与补齐办法

| 优先级 | 当前不足或问题 | 可能后果 | 乙方负责的补齐工作 |
|---|---|---|---|
| 首要 | 差异化仍是价值假设，缺少竞品实测和用户迁移理由 | 功能完成后用户仍留在原工具 | 对比同一组任务，寻找真实时间、成功率和恢复成本差异 |
| 首要 | 首发用户、界面和系统平台未确认 | UI 与测试范围无法收敛 | 提交用户场景和不同首发组合的代价建议 |
| 首要 | “不会被上游打烂”没有支持范围 | 形成无法兑现的承诺 | 分别定义环境固定、升级验证、接口适配的覆盖 |
| 首要 | 独立运行时及数据边界未验证 | 配置虽独立，全局更新仍可能影响旧环境 | 实测并记录执行文件、依赖、数据和启动来源 |
| 首要 | 市场自身更新与恢复机制未定 | 故障时用户无法打开恢复页面 | 先验证外部恢复入口和市场自更新失败场景 |
| 首要 | 检测器尚未证明能识别真实故障 | 产生“已验证”假象或错判插件 | 先建立正常、已知失败、测试未完成三类对照 |
| 高 | 插件目录来源、更新与作者身份流程缺失 | 内容陈旧、冒名、重复或断链 | 定义最小收录字段、来源记录、认领与下架流程 |
| 高 | 适配层覆盖和作者采纳成本未知 | 做出接口却无人愿意接入 | 用真实插件完成接入，并比较修改量与功能限制 |
| 高 | 单插件通过与组合可用被混为一谈 | 真实用户装多个插件后冲突 | 增加典型组合和共享依赖、配置冲突测试 |
| 高 | 其他市场、CLI 与用户手工修改并存 | 覆盖配置、状态失真、恢复错误 | 识别外部变化，更新前核对基线，冲突时停止该操作 |
| 高 | 检测与运行插件的隔离边界未定 | 测试污染用户环境或暴露凭据 | 在独立测试环境运行，明确文件、网络、进程与凭据边界 |
| 高 | 支持周期与旧版退场政策缺失 | 维护范围不断累积、用户被突然抛弃 | 制定支持窗口、弃用提示和迁移建议 |
| 高 | 持续运营的人力和费用没有安排 | 目录、故障、测试任务无人长期处理 | 建立按实际成本更新的资源表和任务责任人 |
| 高 | 多类资源被统一成相同安装与兼容逻辑 | Skill 添加却不能调用，Prompt 保存却无使用入口 | 为六类资源分别定义实际生效、停止和移除标准 |
| 高 | 能力包与独立资源重复安装、共享依赖归属不清 | 重复命令、版本冲突或误删共享内容 | 记录来源包、资源身份与使用关系，变更前展示影响 |
| 首要 | 六类资源的自动发现、获取和实际使用尚未形成完整流程 | 有目录和成功提示，用户却无法完成任务 | 将来源连接列为独立验收项，再逐类完成获取与使用实验 |
| 高 | 多来源字段、分页、认证和更新方式不同 | 搜索漏项、来源失效或缓存被误当新结果 | 建立来源适配与查询范围记录，验证限流、重试和缓存新鲜度 |
| 高 | 目录范围和调用资格混淆 | 将 MCP 条目可见当作已获授权，将命令描述当作已注册功能 | 记录来源查询范围、运行位置、账户条件与实际调用结果 |
| 高 | Prompt、Skill、Slash 的归属与执行方式混淆 | 重复安装、覆盖草稿或在用户未发起任务时执行 | 分别验证模板输入、Skill 调用和命令执行，显示所属包与依赖 |

| 中 | Pivot 已有局部源码核查，完整可复用性仍未验证 | 将设计入口误当成熟功能，或为复用引入复杂度 | 分别评估产品设计、代码依赖、测试、许可证与接入成本 |
| 中 | 产品命名、授权方式与收益目标未定 | 影响发布方式、贡献流程和预算 | 在核心价值验证后给出具体选项及影响 |

### 历史对话中不应继续沿用的结论

- “已经有八个”“某项目下载最多”“某功能无人做”：缺少完整、当前且一致口径的核查，不能作为本项目立项结论。
- 发版间隔不能推导破坏频率，也不能直接推导适配工作的固定时限。
- 安装成功、配置合并成功、代码加载成功、功能正常是不同证据层级。
- 单个测试通过率不能单独决定整个产品有无价值；应考虑它测了什么、故障严重性及用户任务。
- 隔离一个数据目录不等于对任意插件代码建立安全沙箱。
- 签名、哈希与到期策略不能替代测试，也不自动证明发布者的声明真实。
- 市场掌握操作流程不要求禁止所有外部工具；需要的是可识别、可协调的修改边界。
- 市场和兼容层都需要持续维护，不能把前者估为一次性成本、后者估为无限义务。
- 第三方是否接受具体合作、PR 或协议扩展，必须以对方实际回应为准。

## 9. 市场调研工作计划

当前完成第 6 节的初步文档核查，第 4.4 节的 Codex 与 Pivot 参考核查，以及第 4.6—4.7 节的来源与 DSH 扩展核查。宿主已接入三个指定来源的选集更新、版本缓存和资源获取；任意来源、全站发现、以下调查、访谈和竞品实测尚未完成。

### 9.1 竞品与替代方案

从历史对话候选中筛选 3—5 个仍能获取和安装的产品，另保留 DSH 原有操作方式作基线。dsh-market 为已确认的候选；DSH-Store、dsh-unified-market 等仍需先核实实际可用性。协议项目与终端界面作为生态依赖单独分析，不混入直接市场数量。

对每个样本固定版本、环境、来源和观察日期，走同样的任务：安装市场、寻找指定用途插件、完成配置、管理外部已装插件、更新、处理失败、恢复。结果写成可复现记录，比较：

- 首次使用需要几步、卡在哪里、是否需要离开产品找资料。
- 内容是否可安装、是否重复、支持条件是否可理解。
- 操作显示与实际状态是否一致，失败后用户如何恢复。
- 上游或插件升级时，它提供哪些具体保护，覆盖哪些情形。
- 哪些机制能复用、哪些体验已有优势、我们还有什么理由让用户迁移。

评价材料区分维护者声明、我们的实测、用户反馈三种来源。星数反映关注度，下载量可能包含自动任务，issue 数不等于差评数量；不能直接排名为“评价最好”。

体验参照单列 Codex 与 Pivot，研究用户如何理解资源、阅读详情、完成安装后使用及管理已有资源。插件、Skill、MCP、Slash 和 Prompt 分别验证用户需求与供应来源；不能把可执行插件的故障统计直接推广到其他资源，也不能据此宣称六类市场是无人涉足的空白。

### 9.2 用户与作者研究

建议第一轮邀请 5—8 位使用者、2—3 位插件作者，属于发现问题的小样本，不用于推算市场规模。联系他人前由甲方明确授权；乙方先准备邀请文案、任务和记录表。

重点观察过去发生过的任务：最近一次怎么找到插件、哪里失败、如何恢复、花了多少时间、为什么仍用当前工具。再用原型观察能否完成任务，避免只问“你喜不喜欢这个想法”。作者侧重点是提交负担、支持版本声明、真实接入改动与故障报告可用性。

交付研究报告应同时列出支持和反对本方案的证据。即便兼容故障很少，发现效率、配置体验和恢复能力仍可以单独评价；若整体迁移理由不足，应调整定位或投入强度，而非制造差异化结论。

## 10. 技术验证计划

以下为待执行实验。乙方负责技术选型、脚本、测试与记录；甲方判断结果是否满足产品承诺，无需决定内部工具名称。

| 实验 | 验证的问题 | 必须交付的证据 | 对方案的影响 |
|---|---|---|---|
| E1：产品入口和管理闭环 | 能否在目标 DSH 界面安装、配置并管理真实插件 | 固定环境的操作记录、安装前后状态、正常与失败案例 | 确定首发入口、插件形态与管理范围 |
| E2：检测器有效性 | 能否区分安装失败、加载失败、功能失败与测试未完成 | 正常对照、人工故障对照、至少一例可获取的真实版本兼容问题 | 确定测试标签能承诺到哪一层；人工故障不能代表生态破坏率 |
| E3：兼容层收益 | R35 双路径能否在同一环境管理并共存；共享适配能否在两个明确宿主版本完成同一功能 | 先验证真实原生与标准样本及混合组合，再记录跨版本插件/适配器改动、直接接入基线、实际结果及未覆盖变化 | 确定实现方式和支持范围，衡量是否减少重复适配；两条接入路径分别报告结果 |
| E4：环境保留与恢复 | 新版安装、升级或失败是否影响旧环境和数据 | 运行时路径与依赖记录、恢复前后功能检查、市场页面不可用案例 | 决定环境保护与恢复的实际宣传范围 |
| E5：组合与外部修改 | 插件组合、CLI 和其他管理器操作后，状态能否正确识别 | 冲突样本、外部修改检测、无关配置保留、重复操作结果 | 确定可接管范围及操作冲突策略 |
| E6：六类资源真正可用 | 插件、Skill、MCP、Slash、Prompt 是否各有完整使用流程 | 配合 E1/E8，验证模板变量与缺项、输入预览、不覆盖草稿、用户发送、更新与移除；展示跨类关联及共享资源移除案例 | 决定六类的具体支持格式与深度，未完成项不标为已支持 |
| E7：外部来源自动发现 | 六类资源能否从选定发布源持续获得真实可追溯条目 | 按来源能力记录列表、搜索、分页、详情与刷新；覆盖所属包提取的 Slash/Prompt、字段缺失、重复来源、限流和单源失效 | 确定来源覆盖、同步方式及费用；发现通过不替代 E6/E8 的使用验收 |
| E8：DSH 扩展实际生效 | 原生命令、Skill 与 MCP 在选定宿主组合中是否形成完整流程 | 命令注册/可见/执行/卸载与重名案例；Skill 完整资源目录及范围/调用策略；MCP stdio、HTTP 工具调用与能力缺口案例；R35 的标准路径另测具体界面映射与能力缺失 | 确定哪些扩展直接接入、哪些需要适配，不能以有接口代替产品验收 |
| E9：来源与账户生命周期 | 六类资源来源更新、私有条目与服务认证能否正确管理 | Skill 完整目录与更新、MCP Registry 状态同步、凭据失效与撤销、公共/私有数据边界、目录服务离线；不重复 E7 的基础查询测试 | 固定连接与恢复承诺；服务条目可见不代表有权调用，未实测来源保持候选状态 |

v0.6 按 R17 重定 E6/E7/E9 的对象，保留编号便于追溯。此前模型下载、运行和主题实验均暂缓；R33 现恢复主题实验，沿用以下跨资源验收场景：

- E1/E6/E8：从实际使用入口执行任务并取得结果；记录 DSH 已配置模型的必要任务能力，MCP 样本注明实际协议版本和扩展要求，Prompt 与 MCP Prompts 分开验收。
- E4/E5/E6：在下载、配置和激活边界中断后重新进入，识别部分成功、保留已有资源并恢复；远端结果未知时避免盲目重复提交。
- E7/E9：用中文、别名、重复来源、未知兼容状态和单源失效检验搜索；同时记录目录查询路径与凭据使用对象。
- E4/E9：分别展示本地可恢复内容、远端不可固定依赖，以及目录服务不可用时已安装资源的可用边界；不把重新保存配置视为恢复已退役云服务。

建议技术样本从 6—12 个不同接入形态的插件、2—3 个确定版本开始。此数量仅用于控制首轮实验规模，不是覆盖承诺或生态统计样本；先跑少量校准检测流程，再扩大。

测试实际执行代码时使用独立环境和专用测试数据，不能把用户日常 DSH 配置与凭据当成默认测试材料。配置目录隔离、进程隔离与系统权限隔离分别说明；未建立对应边界时不宣称“安全沙箱”。

功能测试使用可观察的成功条件，例如命令返回正确结果、设置项实际生效、工具完成指定操作。缺少外部服务或凭据的测试记录为未完成；替身服务结果与真实服务结果分别标注。

首次实验记录冷安装、缓存安装、启动、测试、恢复的耗时与资源，再决定并行度和复测频率。检测成本按样本实测计算，不沿用历史助手的“每格十五秒”等未证实估计。

若 E3 失败，先说明具体接口或宿主缺口，修订兼容层范围；若 E4 不能恢复某种数据，则缩小恢复承诺或补充迁移机制。实验失败影响对应功能，不自动否定 R1—R4。

## 11. 内容运营、作者参与与信任

目录同时支持用户社区投稿、外部来源自动汇总和平台维护的精选推荐。社区投稿是 R18 明确要求，六类均需有用户可操作的提交入口；人工后台处理不替代用户投稿能力。外部条目无需先经人工逐个上架才能被发现；精选推荐、实际测试和安装资格各有依据。记录原作者及来源、可固定的发布版本、安装条件、支持声明、许可与维护状态；引用、缓存或重新分发分别核查使用条件。

自动来源流程为：连接 → 获取与字段校验 → 展示来源及验证状态 → 持续更新。人工运营负责作者提交、纠错、精选推荐、争议与下架处置，第一版无需复杂审核后台；自动来源更新不能依赖逐条人工录入。插件记录分发包、宿主及执行依赖；Skill、命令记录完整资源、归属及调用方式；MCP 记录包或地址、传输、配置与所需能力；Prompt 记录模板内容、变量、示例、来源及使用条件。

### 11.1 社区上传、发布与维护

建议共用“分享资源”入口，根据类别选择内容形式：Prompt 可直接填写或上传模板；Skill 提交完整资源目录；插件提交可安装包或发布仓库；MCP 提交服务包或连接定义、配置说明；Slash 提交可注册的实现或所属插件；主题提交插件或配色文件、读取它的父插件与恢复说明。六类均允许社区贡献，但不要求所有资源使用相同文件格式，也不将上传 MCP 资料解释为替作者托管远端服务。

建议流程为：准备内容 → 填写用途、示例、来源与版本 → 预览提交 → 查看检查和发布状态 → 用户发现使用 → 反馈与作者更新。普通用户无需编写代码即可分享 Prompt；涉及执行代码的资源仍需提供对应实现。作者身份、本人有权分享的内容、必要检查与发布规则需在实现前具体设计，不因支持上传就承诺任何内容提交后立即公开或执行。

首发至少支持保存草稿、投稿结果、明确的修改原因、作者更新和撤回、用户问题反馈。版本更新应区分作者发布的新版本与用户正在使用的版本，保留用户修改过的副本。来源自动发现与作者投稿指向同一资源时关联身份和版本，避免重复上架；私有凭据由使用者连接时填写，不随共享模板或配置公开。

### 11.2 内容与使用规则

具体规则建议：

- 同一插件的 npm、GitHub 等来源需有身份关联依据，保留原始来源，不凭同名自动合并。
- 作者认领需证明发布权限；平台测试结论与作者声明分别展示。
- 收录内容不代表官方认证；兼容测试通过也不等于安全审计通过。
- 下载内容固定版本和完整性记录，安装脚本的执行规则明确；目录描述中的命令不作为自动执行指令。
- 发现异常版本可暂停新安装并通知受影响用户，保留处理记录；不擅自删除用户已有数据。
- 日志和测试结果默认留在本地；共享前解释内容和用途，清理凭据、聊天内容及不必要的本地路径。
- 停止支持旧版需要提前说明支持范围、已知问题和迁移选择，不能以强制升级代替维护政策。

兼容层作者工具从一个真实插件样例和一条可运行的验证流程开始。作者应能知道要改哪里、能获得什么保证、超出范围如何处理。投稿所需的身份、更新管理和反馈属于首发；更完整的后台与社交功能根据实际参与规模再扩展。

### 12.2 产品验收与工程验证

验收对象是支持矩阵内的真实用户流程。以下为必需的验收类别，具体样本和操作标准在 A 阶段固定：

1. 能从 DSH 内对插件、Skill、MCP、Slash、Prompt、主题六类分别完成发现、获取、必要配置、使用、管理和移除，按第 4.3 节区分具体动作。
2. 已安装状态与实际环境一致，外部修改和加载错误能被识别。
3. 已知失败插件不能显示成功；未完成的测试不能显示已验证。
4. 升级失败和恢复案例有可重复结果；无关配置与数据不被本次操作破坏。
5. 若宣称兼容层保护，须用明确版本与功能展示实际收益和限制。
6. 若宣称环境固定，须证明全局工具更新不会悄悄替换该环境运行时。
7. 市场页面不可用时仍有经过验证的恢复办法。
8. 发布说明、产品界面与支持政策使用同一份能力事实。
9. 对交付范围内的外部来源，真实完成自动发现、搜索、分页、详情及更新；单个来源失效、凭据失效和缓存过期均有正确状态，不能用静态样例通过。
10. Prompt 可预览和填参，缺少变量时明确提示；加入当前任务时不覆盖已有草稿，未经用户发送不执行；不依赖 MCP Prompts 桥接。
11. Skill、MCP 和 Slash 验收关联目标 DSH 版本及实际接口；同名冲突、缺少依赖、协议能力不支持及移除后的状态均可解释。
12. 插件包与其 Skill、Slash、Prompt 关联清楚，更新和卸载保留共享资源；六类来源接入由乙方完成设计，不将模型目录或下载配套重新混入首发。
13. 每类交付流程有明确的开始入口、执行方和结果去向；中途失败后能识别部分完成状态，继续操作不会误删共享内容或盲目重复远端执行。
14. 凭据只交给对应接收方，私有目录与工作内容不会因公共目录同步被混入公共数据；资源或服务切换遵循用户已选定的成本和数据去向条件。
15. 环境保护明确哪些内容能固定或恢复；依赖外部在线服务的可用性限制可见，平台目录停服不会被伪装为本地资源已经失效。
16. 六类各完成作者投稿、发布后被发现、实际使用、反馈与版本更新的样本流程；投稿失败可修改，只有有权维护的作者能更新，草稿和私有凭据不进入公共目录；作者更新不覆盖用户自行修改的副本。
17. 统一兼容层分别完成原生 DSH 资源和 dsh-std 组件的真实使用流程及混合共存测试；接入路径可追溯，协商、安装、激活和功能实测不混淆，缺少适配器或能力时明确处理，更新和卸载不损坏共享依赖或另一条路径的资源。

实现阶段建立一个统一验证命令，由本地、CI 和提交检查共同调用。测试包括操作行为、模块契约、配置写入边界、典型组合和必要的端到端流程；测试结果不以只有模拟数据、非空断言或界面截图代替。

### 12.3 判断用户价值的指标

| 指标 | 定义与解释 |
|---|---|
| 首次任务完成情况 | 观察用户能否独立安装并实际使用目标插件，记录失败步骤 |
| 找到可用插件的时间 | 从提出用途到选出并确认可用的插件，与原有方式对比 |
| 自动发现有效性 | 在明确来源和查询范围内，用户能否找到目标资源；记录漏项、重复、过期信息及来源故障，不以目录总数代替质量 |
| 安装与更新成功情况 | 区分成功、用户取消、网络失败、配置缺失和实际兼容失败 |
| 恢复能力 | 能恢复的故障类别、恢复耗时，以及不能恢复的影响 |
| 兼容层收益 | 同一场景直接适配与共享适配的修改量、功能覆盖和维护负担 |
| 持续使用意愿 | 用户是否愿意继续管理真实环境，为什么留下或离开 |

目前没有基线，不设置用来制造“通过”的百分比。小样本用于发现问题；后续确定可量化目标时同时公开样本量、测试范围和未完成项。数据采集不能默认上传用户活动。
